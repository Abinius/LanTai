4. M1 内核 MVP：采集→台账（commit 4013393）
================================================================

pipeline/ 13 文件：
  run.py            编排器（argparse --from/--to 或 --days，串 p1→p3）
  config.py         信源注册表 + LLM 凭证读取（llm key.txt 或 LANTAI_LLM_KEY）
  contracts.py      RawItem / DataPoint / Ledger 等 dataclass
  llm.py            sensenova 客户端（stdlib urllib，thinking:disabled，退避 3 次）
  modules/p1_interval.py
  modules/p2_collect/{base.py, xwlb.py, rmrb.py}
  modules/p3_extract.py
  prompts/extract.md

设计要点：
  · 模块间只传结构化 dataclass，任一步可独立替换/重跑
  · 采集零依赖：全 stdlib（urllib.request + html.parser.HTMLParser + re）
  · base.py 容错：记录 HTTP 状态码 + 字节数 + 选择器匹配数到 run.log；
    连续 3 个 404 停止翻版
  · p3 限流降级：LLM 失败时正则命中片段仍入台账，标 llm_unverified=true，
    不阻断流水线

验收（单日 2026-10-05）：
  xwlb  1 条，published_at=2026-10-05 19:00:00（真实播出时间，非抓取时间），
        body=496 字（brief 提要）
  rmrb  37 篇，8 个版面，page 9-11 连续 404 自动停
  ledger  4-10 个数据点，**人工核对原文全部命中**：
          "3.4%" / "5.3%" / "196.3" / "348.3" / "78个步行街" 全在
          content_30184222.html 正文中 → 无 LLM 幻觉

验收（5 天 2026-10-01~05，含后续里程碑重跑）：
  189 raw（5 xwlb + 184 rmrb），49 台账点，全部 llm_unverified=false
  （sensenova 本期未触限流）

5. M2 研判：三维交叉（commit 917069a）
================================================================

新增：
  modules/p4_analyze.py    三维交叉研判
  prompts/analyze.md       研判分析师角色 + 红线
  contracts.py             加 Analysis / Prediction
  run.py                   接入 P4，加 --reanalyze

三维交叉方法（PRD §3.4）：
  1 数据说什么——哪些强、哪些弱、矛盾在哪
  2 官媒说什么——主线、措辞升级、政策指向
  3 两者是否同频——印证 or 背离（背离处即机会/风险）

LLM 输入压缩（控成本）：
  数据面 = 台账点（indicator/value/yoy/agency + source_url）
  官媒面 = 联播提要全文（已精简）+ 人民日报标题清单（不送正文）
  输出 = core_judgments / structural_findings / predictions[{text, data_refs}]

红线（prompts/analyze.md）：
  · predictions ≥5 条，每条必须引用台账里至少一个 source_url
  · 不可编造数据；台账里没有的数字不能出现在预测里
  · 背离优先（这是判断的价值所在）
  · core_judgments ≤3 条，少而准
  · 措辞克制：用"数据显示""官媒主线指向""存在背离"，不用"必将""暴涨"

验收（5 天数据）：
  3 核心矛盾判断 + 5-6 结构性发现 + 7-10 条趋势预测，每条带可溯源 source_url
  样例（背离心发现）：
    "2500亿超长期特别国债已全额下达，但社零仅2.5%、公路流动-1.1%，
     政策投放与实物消费背离延续风险"

6. M3 出刊引擎：模板驱动深度报告（commit d63c88c）
================================================================

新增：
  modules/p5_publish.py          模板渲染 + 变量注入
  templates/report-template.md   报告骨架（{{var}} 占位）
  prompts/publish.md             出刊主编角色
  contracts.py                   加 Report
  config.py                      加 TEMPLATES_DIR
  run.py                         接入 P5，产出 report.md + report.json

★ 关键设计取舍：数据表与源列表**程序化渲染**，不走 LLM
  · 数字从 ledger 确定性生成 → 报告里没有一个数字可能被幻觉
  · 只有"标题 + 核心摘要"走 LLM 短调用（max_tokens=800），失败时程序化兜底
    （标题取首条判断前 25 字，摘要拼前两条结构性发现）
  · report.md 是文件交付物；Laravel 站不解析它，改读结构化 JSON，
    避免多一套渲染链路

报告结构（PRD §6）：
  核心摘要 / 一 核心矛盾判断 / 二 结构性发现 / 三 趋势预测（带数据支撑）
  附 数据台账 / 附 数据溯源 / 口径说明（区分"表述"与"事实"）

验收（5 天数据）：
  10693 字报告，12 个去重数据源，每条论断可溯源
  标题示例："服务业扩能与社零偏冷的张力和分化：2026国庆周观察"

7. 承自 AIHOT 时代的踩雷（v3.0 已落地为代码）
================================================================

以下四条在旧 AIHOT 开发日志里，v3.0 重构时没有忘掉，都已写进代码：

雷1 RSS/聚合源可能是死快照
  旧事：新华社 RSS 冻结在 2022-12-14，300 篇全是老稿，无 <pubDate>，
        AIHOT 用 discovered_at 冒充 published_at → 首页 2021 老稿像当天新闻
  v3.0 落地：
    · xwlb 用 CNTV API 的 time 字段作 published_at（真实播出时间）
    · rmrb 日期从 URL 路径 YYYYMM/DD 取，不用抓取时间
    · 任何一处都不做"用抓取时间回填发布日期"

雷5 sensenova 必须 disable thinking
  旧事：不加 thinking:disabled，max_tokens 全花在 reasoning 上，
        finish_reason="length"，content 为空
  v3.0 落地：pipeline/llm.py 里 "thinking": {"type":"disabled"} 硬编码进
        请求 body，所有 LLM 调用自动生效，不需要调用方记得

雷9 时效性红线（旧时代最严重的事故）
  旧事：用 timeline_at（抓取时间）批量回填 published_at，让 9 月 8 日印发的
        文件显示成"今天发布"，绕过了引擎"backfill 无真实日期不上精选"的保护
  v3.0 落地：
    · contracts.DataPoint.pub_date 解析不出就留 None（不留假值）
    · prompts/extract.md 明文写红线：pub_date 必须真实，禁止用"今天"或
      抓取日期冒充；解析不出填 null
    · 站端口径说明区也写死："未核验点为模型抽取失败时的正则命中片段，
      已单独标记，请谨慎引用"

雷4 "curl 抓到" ≠ "程序抓到"
  旧事：阿里云 WAF 对 UA 差异化处理，curl 到 72KB HTML 而引擎报 no items matched
  v3.0 落地：base.py 每次请求都记录 HTTP 状态码 + 字节数 + 选择器匹配数到
        run.log，便于诊断"到底有没有抓到"

8. v3.0 新增踩雷
================================================================

🚨 雷 A：人民日报路径迁移（会导致整源全 404）
  旧路径 rmrb/html/YYYY-MM/DD/nbs.D110000renmrb_*.htm 已 404。
  照抄历史文档/旧代码会整个源静默失效。
  新路径见第 3 节。
  教训：信源站点结构会变，路径要定期探测；探测结果要写进日志而不是只靠记。

🚨 雷 B：argparse 的 dest 与 flag 名不一致
  --from/--to 里 from 是 Python 关键字，dest 必须显式给 "from_"，
  但 --to 没指定 dest 时属性名就是 "to" 而不是 "to_"。
  两种命名混用时极易写错，直接 AttributeError。

🚨 雷 C：python 脚本导入路径
  `python pipeline/run.py` 时 sys.path[0] 是 pipeline/ 而**不是** repo root，
  `import pipeline.xxx` 会失败。run.py 里手动 insert repo root 到 sys.path；
  config.py 的信源注册表路径要写全 `pipeline.modules.p2_collect.xwlb.XwlbCollector`。

🚨 雷 D：Windows 控制台 cp936 乱码
  run.py 输出中文全乱码，但落盘文件都是正常 UTF-8。
  修：run.py 开头 sys.stdout.reconfigure(encoding="utf-8")。
  注意：`python -c "..."` 交互调试不走这段代码，仍然乱码（无害，但要看懂）。
  读 UTF-8 文件时记得同样 reconfigure，否则 print 出来是乱码、以为数据坏了。

🚨 雷 E：optimize-autoloader:true 固化 classmap（M4 最坑的一个）
  Signify 的 composer.json 配了 optimize-autoloader:true。
  删掉 app/Providers/AuthServiceProvider.php 后 artisan 全线报
    "Class App\Providers\AuthServiceProvider not found"
  原因是它被显式登记在**两个地方**：
    · bootstrap/providers.php
    · config/app.php 的 'providers' 数组
  两个都改了 + php composer.phar dump-autoload + 清 bootstrap/cache/
  才恢复。
  教训：删/加 app/Providers/*.php 后必须重生成 autoload。

🚨 雷 F：Tailwind 颜色令牌是嵌套对象
  tailwind.config.js 里是 status: { warning: '#A8791E' }
  所以类名是 bg-status-warning/5，**不是** bg-warning/5。
  写错时不报错，只是样式不生效，很难发现。

🚨 雷 G：改了 Blade 视图必须重建 CSS
  Tailwind 构建时按源码扫描生成工具类，新加视图里的类不在已编译产物里。
  本机无 node_modules（Signify 只提交了编译产物），需先 npm install
  再 npm run build:css。改视图后忘建 = 页面样式静默丢失。

🚨 雷 H：Git Bash 的 locale 是空的，中文传 curl 会被破坏
  locale= 时 `curl "http://x/?q=服务业"` 传出的字节不是标准 UTF-8，
  后端检索误报 0 命中（看起来像检索功能坏了）。
  用显式百分号编码（?q=%E6%9C%8D%E5%8A%A1%E4%B8%9A）或 PHP 侧 rawurlencode
  复现正确行为。踩过一次，排查了很久才发现是 shell 编码问题。

🚨 雷 I：php artisan serve 用 pkill 杀不掉
  Windows 下 pkill -f "artisan serve" 无效，端口仍 LISTENING。
  正确做法：netstat -ano 找端口 PID，taskkill //PID <pid> //F
  （注意 taskkill 在 Git Bash 里要写 //PID //F 双斜杠）

🚨 雷 J：LLM 输出有随机性，别把预测条数当稳定性指标
  同一批 49 个台账点重跑 P4，predictions 从 7 条变 10 条，findings 从 6 变 5。
  内容质量稳定但条数浮动。验收看"是否 ≥5 且每条带 source_url"，不看固定条数。

🚨 雷 K：dataclass 加必填字段会连带打挂兜底构造
  Report 加必填 summary 后，run.py 里出刊失败的兜底
  Report(period=..., title=..., content_md="") 直接 TypeError。
  改契约时全仓搜构造点，别只改主路径。

🚨 雷 L：composer 的 post-autoload-dump 会跑 artisan package:discover
  如果 app 起不来（比如雷 E 未修），dump-autoload 也失败，
  看起来像"composer 有问题"，其实是应用启动失败。
  报错要往上看第一行异常，不是看 composer 的退出码。

13. M5 交付后找 bug 一轮（2026-10-06）
================================================================

方法：先跑两套测试确认基线（PHP 13 例 / 内核 19 例全绿），再按「写测试暴露
→ 确认失败 → 修 → 复跑」逐个钉死。五个真 bug，都在测试里留了回归用例。

13.1 雷 V：民族自治区全称被剥成半个名字（内核 p3）
  `_normalize_region()` 按后缀剥离时，「广西壮族自治区」→ 后缀是「自治区」，
  剥掉得「广西壮族」；宁夏回族/新疆维吾尔同理。这个结果既不在站端
  REGIONS 候选表里（无法订阅），又与同一份台账里 LLM 直接吐的「广西」
  分裂成两个地区标签。同批的西藏自治区/内蒙古自治区恰好正确，所以一直没露馅。
  对策：加 REGION_ALIASES 显式映射三个带民族名的自治区，剥离前先查表。
  测试：TestRegionNormalize 5 例（含「京津冀地区」「省」不被误剥）。

13.2 雷 W：找回密码不认大小写不同的邮箱（站点）
  注册把邮箱归一小写存储，登录的 LoginRequest 也归一小写，唯独找回密码
  这条链（PasswordResetLinkController + NewPasswordController）没归一。
  SQLite 字符串比较区分大小写（MySQL 默认 utf8mb4_unicode_ci 不区分），
  于是本地出现「注册得进、密码找不回」，报「找不到具有该电子邮件地址的用户」。
  对策：抽 `User::normalizeEmail()` 一处实现，注册/登录/找回密码四处共用。
  测试：test_password_reset_accepts_differently_cased_email。

13.3 雷 X：报告卡折叠标签会吃掉「命中标签」（站点）
  卡片最多显示 6 个标签，多出折叠成 +N。但命中标签排在领域+地区拼接的
  原顺序里，30 天期有 9 领域 + 20 地区，「山东」这种排在第 10 位之后——
  于是卡片出现在「我的情报」里，却一个高亮都看不到，用户无从判断
  这期为什么入选（订阅金融+云南时两个命中都会被折叠掉）。
  对策：usort 把命中标签排到最前，再截断。
  测试：test_matched_tags_are_never_folded_away（8 领域 + 6 地区，
  命中项排在最后的极端构造）。

13.4 雷 Y：p4 的 data_refs 未校验类型，一个 null 废掉整期研判（内核）
  这是本轮最重的一个。`_parse()` 里 `p.get("data_refs", [])` 直接遍历：
  · LLM 把单条引用写成字符串（而非数组）→ 逐字符拆成几十个「URL」，
    渲染到站上是一堆单字符链接，且全程不报错；
  · 写成 null → 遍历 None 抛 TypeError。
  后者更致命：run.py 的 try/except 会把异常吞成空 Analysis，接着触发
  §11.3 雷 N 的护栏「台账非空而研判为空」→ 跳过 P5 返回 1。
  也就是说 LLM 少写一个字段，整期报告就不出了。
  实测现有两期产物未中招（LLM 恰好一直给数组），属潜在雷。
  对策：抽 `p4_analyze.normalize_refs()`：字符串当单条引用收下，
  null/非列表归空，非字符串元素丢弃；p4 写与 run.py 读回共用同一实现。
  测试：TestPredictionRefs 5 例 + TestPipelineLoaders 3 例（含 --republish
  读回路径的脏产物容忍与 region 不丢字段的回归）。

13.5 雷 Z：rmrb 正文解析丢段落分隔（内核 p2）
  `_ArticleParser.text()` 用 `"".join(self._chunks)` 直接拼接 HTML 文本节点。
  当 HTML 里标签间没有空白（`<p>A</p><p>B</p>`）时，两段会连成 "AB"，
  完全没有分隔符——LLM 抽取时无法区分段落，可能把不同段落的内容混在一起。
  实测现有数据未暴露（人民日报正文 HTML 恰好有缩进空白），属潜在雷。
  对策：handle_data 里过滤纯空白文本，text() 改用 `"\n".join()` 拼接，
  段落间用换行分隔；原有的三重换行压缩逻辑不变。
  测试：TestArticleParser 4 例（含紧凑 HTML、带缩进 HTML、容器外文本排除、
  换行压缩）。

13.6 复跑结果
  · PHP：16 例 52 断言全绿（本轮新增 3 例）
  · 内核：36 例全绿（本轮新增 17 例）
  · `--republish` 端到端复验：58 点、judgments=3/findings=5/predictions=7、
    退出码 0，读回路径无异样
  · 顺带确认解析层现状：p3（isinstance list/dict + _clean）、
    p5（str(x or "")）都有类型防护，只有 p4 漏了，已补；
    p2 rmrb 的 HTML 拼接也漏了分隔符，已补。
  · llm.py 的 chat_json 代码块剥离逻辑：split("```", 2) 取 text[1] 后
    没用 text[2]，格式不标准时会解析成空——但实际 LLM 输出总是标准围栏，
    未暴露，暂不修。

    通用 `?t=YYYYMMDD`。30 天旧台账抽样：366 个 pub_date 空里，362 个能从
    URL 里救回来——URL 是采集器从信源直接复制的字段，不是抓取时间冒充。
  · 新增 `_safe_date(s)`：校验 YYYYMMDD 合法性（月 1-12、日 1-31），
    RawItem.date 由 p1 生成恒合法，仍加守卫防未来格式漂移。
  · pub_date 三级回落：`_clean(dp["pub_date"]) or _url_date(url) or _safe_date(item.date)`。
    LLM 抽到优先；URL 显式日期次之；item.date 是 xwlb 无 URL 日期时的兜底
    （广播日是最接近的合法日期，xwlb 一天一条，广播日即发布日）。
  · extract.md 加 agency 推断指引：优先从"国家统计局发布""央行数据"等表述
    推断；**不要把"人民日报""新华社"等媒体本身当成数据来源机构填进 agency**。
    实测老代码有 17 个点把"人民日报"填进 agency，新代码一次都没再出现。

14.2 P1-2 口径根治

  · p3 新增 `CITY_TO_PROVINCE` 79 项：覆盖直辖市、主要地级市、民族自治州、
    边境口岸（吉隆口岸/霍尔果斯/满洲里）、功能区块（前海合作区/粤港澳大湾区）。
  · REGION_SUFFIXES 加"县"：让"南京县"这类县级行政区能剥离到"南京"再归到江苏。
  · `_normalize_region(region, indicator="")`：接受 indicator 参数，让"县域"
    点若 indicator 里带可识别地名（如"前海合作区 GDP"）则升级为所属省。
    升级失败（抽不出地名）保留"县域"。30 天台账 170 个县域点里能识别地名
    的 23 个（13.5%），其余保持县域类别。
  · 站端 REGIONS 34 省级候选不动，地市数据统一归到省级后自然可订阅。

14.3 P1-3 数据清洁

  · `_validate_unit(unit, raw_text)`：只修"美元"被拆掉"亿/万"的明确错误
    （LLM 拆"4323.1 亿美元"为 value=4323.1 unit="美元"，丢"亿"），其它一律
    原样——过度白名单校验会误杀真单位（美元/吨、亿千瓦时等）。
  · `_dedupe_points(points)`：按 `(indicator, value, source_url)` 三键去重。
    同一段 raw_text 拆出的不同指标不算重复（不同维度）；同一 URL 里 LLM
    重复抽出同指标是主要来源。
  · extract() 末尾去重：`ledger.points = _dedupe_points(ledger.points)`。
  · p5 `_render_data_table` 加跳过逻辑：非未核验点的 value 为空则不入表，
    避免渲染出"None 亿元"这种脏行。

14.4 新踩雷

  · **雷AA（本轮）**：LLM 偶尔把字段值输出为 JSON null 而非省略该键，
    `str(dp.get("value"))` 得到字面字符串 "None" 落进台账。渲染到报告里
    是"云南对缅甸贸易额 | None | 亿元 | 31.1"——数值列是"None"这个字符串，
    yoy 却正常有值。30 天旧数据实测 26 行此问题。
    原因：indicator/value 用 `str(dp.get(...))` 而其它字段用 `_clean(...)`；
    `_clean` 会把 "null" 字符串与 JSON null 都归一到 None，`str(None)` 又
    变回字面 "None"。
    修：indicator/value 也走 `_clean(...) or ""`，None 归一为空字符串。
    测试：TestLlmNullFields 3 例。

14.5 复跑结果

  5 天期（20261001-20261005，--reextract）：
    · points: 68（旧基线 58-71，因 LLM 有温度）
    · pub_date 空：48.3% → **0.0%**（目标 ≥30% 提升到 ≥70%，大幅超标）
    · agency 空：56.9% → 83.8%（**表面回退、实为提升**：老代码 23 个非空
      agency 里 17 个是"人民日报"误填，新代码 9 个非空全是 海关总署/
      国家统计局/商务部 等真来源；宁可空也不错填）
    · region 分布：全国 40 / 县域 13 / 上海 4 / 地区 3 / 山东 3；
      上海、山东等地级市归到省级成功
    · report.md 4659 字，无 "| None |" 脏行
  30 天期（20260907-20261006，--reextract）：待补录，运行时间长（~15 分钟，
    290 次 LLM 调用），本轮只跑通 5 天期做验证，30 天期在下一批日常任务里
    按新代码自然重生。

14.6 遗留

  · agency 空率高但质量提升：新 prompt 让 LLM 更保守，宁可空也不硬填媒体
    机构。若要真降空率，需要给 LLM 更多"上下文推断"的样例（如"GDP 数据
    通常出自国家统计局"这种常识），但当前阶段优先保住质量。
  · 30 天台账尚未按新代码重抽，pub_date/None 值/去重都还未在 30 天报告里

    `python pipeline/run.py --from 2026-09-07 --to 2026-10-06 --reextract`。
  · CITY_TO_PROVINCE 是维护型字典，新增地市/口岸需要人工补；不做自动识别。

15. v3.1 W3：推送通道（邮件订阅闭环）（2026-10-07）
================================================================

W2 后订阅端仍是拉取式（用户主动刷新 /briefing），PRD §3.9 承诺的「推送到
我的情报」没闭环。本轮 W3 加邮件推送通道，存量订阅 channel 默认 'none'
不推——用户主动改订阅设置才进推送，避免存量用户被突然打扰。

15.1 subscriptions 表加推送列

  新 migration `2026_10_08_000001_add_push_settings_to_subscriptions_table`：
    · channel varchar(20) default 'none'  —— 'none' | 'email'
    · freq varchar(20) default 'weekly'   —— 'daily' | 'weekly'
    · last_pushed_at timestamp nullable    —— 上次推送时间戳，幂等判断用
  存量行 channel 全部默认 'none'，即不推。Subscription model 加 fillable
  与 cast（last_pushed_at → datetime）。

15.2 SubscriptionService 加推送方法

  · CHANNELS / FREQS 常量白名单，`normalizeScalar()` 单值白名单校验
    （不在候选内回落默认值，防脏输入）
  · save() 签名扩到 (user, domains, regions, channel='none', freq='weekly')
  · pushSettingsFor() 返当前推送设置（无订阅记录返回全默认）
  · shouldPushNow(user, now)：channel='email' 且距 last_pushed_at 已达
    freq 阈值（daily 24h / weekly 7d）；从未推送视为「该推」
  · pushableUsers(now)：过滤出该推送的用户 Collection
  · markPushed(user)：写 last_pushed_at
  · FREQ_THRESHOLD_HOURS = ['daily'=>24, 'weekly'=>168]

15.3 订阅设置页 UI + SubscriptionController

  · SubscriptionController::edit() 加 push/channels/freqs 视图变量
  · update() 加 channel/freq 校验与保存（不合法回落默认）
  · edit.blade.php 底部加第三 section "推送设置"：
    单选推送渠道（不推送/邮件推送）+ 单选推送频率（仅在邮件时可用），
    用 has-[:checked] 驱动选中态（与 tag-option 一致），

15.4 Mailable 与邮件模板

  · app/Mail/ReportDigest.php：接收 (User, Collection $reports)；
    Envelope 用 Address 对象（Laravel 11 不接受数组形式）

    · 页脚有退订说明（进 /subscription 关闭推送）

15.5 Artisan 命令 lantai:push

  命令：`php artisan lantai:push [--dry-run] [--period=YYYYMMDD]`
  · 常规模式：过滤 channel='email' 且达 freq 阈值的用户；每个用户推
    last_pushed_at 之后的新期数（首次推送推全部命中）
  · 强制模式 --period=X：向所有 channel=email 用户推这一期，忽略时间窗口
    与订阅过滤（补推/修 bug 用）
  · --dry-run：只打印要推什么，不发；不写 last_pushed_at
  · 单个用户失败 log + 继续下一个；汇总输出 "成功 X / 失败 Y"
  · 未找到 --period 指定的期数时返回 FAILURE（非 0 退出码）

15.6 deploy.sh 加 cron

  在 setup_cron 的 lantai cron 块里加：
    `0 9 * * * cd $WEB_ROOT/site && php artisan lantai:push >> /var/log/lantai-push.log 2>&1`
  每日 9 点跑，命令内部按 freq 判断是否真的推。pipeline 8 点跑完 → 9 点推。
  初始化 log 文件也补上 touch /var/log/lantai-push.log。

15.7 .env.example 加 SMTP 生产配置注释

  MAIL_MAILER=log（本地）+ 注释掉的 MAIL_HOST/PORT/USERNAME/PASSWORD/
  ENCRYPTION 段，用户上 VPS 直接启用即可。

15.8 测试

  · 只推 last_pushed_at 之后的新期数（多期测试）

  · --dry-run 不真发、不写 last_pushed_at
  · 未找到 --period 指定的期数时命令返回 FAILURE
  · 用户订阅轴不匹配期数则不推
  · Mail::fake() 隔离网络；storage/testing/data 假产物目录 tearDown 清理

15.9 遗留

16. v3.1 W4：核验源闭环 + 情报后台最小版（2026-10-07）
================================================================

W3 后 P0-2 的 verify 模块仍是「独立查询」（`--verify <keyword>` 手动跑），
从没进过主流水线；PRD §3.7 的情报后台也一直没建。本轮 W4 把这两块补上，
不碰已稳定的 P4/P5 主链路。

16.1 P2.5 核验源闭环（内核侧）

  新模块 `pipeline/modules/p2_verify_all.py`：在 P3 之后、P4 之前跑，
  按当期台账「主要领域」派生核验关键词，回查发改委/文旅，写出 verify.json。

  **关键词怎么挑（第一版错了，已改）**：初版直接从台账指标名里挑高频词，
  实测挑出来的是「高技术制造业占规模以上工业增加值比重」这种 15-18 字的
  完整指标名——官方列表页标题不可能整句包含，命中率 0。改为：
    · 复用 p3 已有的 `matched_categories()` 挑出当期领域（九类）
    · 每领域从 `DOMAIN_TO_KEYWORDS` 取该领域下**首个出现在台账文本里**的
      具体口径词（增长→GDP / 物价→CPI / 外贸→进出口 …）
    · 不用领域名本身当关键词（「增长」太泛，检索噪声大）
  实测 5 天期派生出 6 词（GDP/投资/零售额/进出口/发电量/就业），
  30 天期 8 词（GDP/固定资产投资/社会消费品零售/进出口/CPI/M2/用电量/税收）。

  **容错**：单关键词回查异常（网络错/编码异常）只跳过该词，不阻断其它；
  整体异常被 run.py 的 try/except 兜住，只 log 不中断出刊。核验失败的报告
  只是少一个附录，不影响主产出。

  **预算控制**：每关键词最多保留 max_hits_per_term=3 条，全局 cap 30 条，
  按 URL 去重（同一文档被多词命中只留第一次）。verify.search 用 max_pages=2
  （比手工查询的 3 页少一页，控制 8 词 × 2 源 × 2 页 = 32 次请求的量级）。

  接入：run.py 在 `run_p3` 为真且台账非空时执行，落在
  `data/<period>/verify.json`。--republish/--reanalyze 不跑（复用已有产物）。

16.2 报告展示核验附录（p5 侧）

  · 两个模板各加 `{{verify_md}}` 占位（文案「附:官方核验参考」）
  · `p5_publish._render_verify(period)` 读 verify.json，按 keyword 分组渲染：
    组头 `**关键词**`，组内每行 `- [标题](url)（机构 · 日期）`
  · 展示上限 VERIFY_SECTION_LIMIT=20 条，超出提示「另有 N 条未展示」
  · 三种降级：文件不存在 → 「本期未回查官方核验源」；hits 为空 →
    「回查官方核验源无命中」；JSON 损坏 → 「核验数据损坏」。都不抛。

  实测（5 天期）：命中 2 条，都来自发改委——
  《中央预算内投资补助和贴息项目管理办法》2025年第38号令、
  《鼓励外商投资产业目录(2025年版)》2025年第37号令。

16.3 情报后台最小版（站点侧）

  新 `AdminController`，两条只读路由，不建表不入库，数据全部来自
  `pipeline/data/` 的目录与 JSON 产物。

  · `/admin/sources` 信源状态：按 `raw/<source>/*.json` 统计各信源累计条数、
    覆盖期数与最近采集时间（取文件 mtime 最大值）。信源清单在
    `pipeline/config.py` 硬编码，本页只展示，不做增删。
  · `/admin/diagnosis` 期数诊断：每期数的原始条数 / 台账点数 / 判断数 /
    预测数 / 核验命中数 / 引用源数 / 报告字数，加上从 run.log 解析出的耗时。

  耗时解析 `parseDuration`：匹配 run.log 里「=== 兰台观局 v*.* 开跑」与
